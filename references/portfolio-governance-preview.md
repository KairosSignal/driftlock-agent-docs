# Portfolio governance (0.5.0)

This optional upgrade reuses existing PLAN/TASK/intake/report authority. It adds no external model API, daemon, database, or visual interface.

Use the new CLI from the candidate worktree:
- portfolio overview ROOT: document-derived project and task counts; no fabricated progress percentages.
- portfolio backlog ROOT: exact links vs possible mentions, declared review/deployment/closure states; completed claims need separate evidence and approval. Unlinked legacy entries are not closed automatically.
- portfolio dependencies ROOT: declared dependency graph, missing references, cycles, active tasks sharing declared parallel_resources; no authorization inferred from lack of conflict.
- portfolio lessons ROOT [--query TEXT]: repeated Rn families are recurrence signals, not shared root causes; explicit root_cause_key and approved lesson captures are searchable.
- portfolio advise ROOT --query TEXT: relevant previous work and lesson suggestions; lexical matching is only a navigation hint.
- portfolio resources ROOT: declared unique resource_scope, token_usage, duration_seconds, cost_amount/cost_currency; no estimates for missing records, no cross-currency totals.
- portfolio link ROOT --project GOVERNANCE --id IDEA-ID --target TASK-ID --expected-sha SHA --approve: explicit relationship in existing authoritative intake, CAS guarded.
- portfolio record-lesson ROOT --project OWNER --id LESSON-ID --cause ROOT-CAUSE-KEY --task-ids TASK-ID --lesson TEXT --prevention TEXT --evidence TEXT --expected-sha SHA --approve: new source report in reports/lessons; capture is unverified, no execution authority. New file expected SHA is SHA256 of empty content. Task IDs must have known matching owner. No implicit overwrite.

Existing task or plan frontmatter can include intake_ids, depends_on and parallel_resources (JSON array or simple legacy flow array); tasks can include root_cause_key and resource measurement fields. Metadata absent from older records stays unknown. Explicit link insertion retains original captured text and hash; no automatic final resolution. Do not treat a report as proof of independent acceptance. No changes to existing problem, plan, review or release gates. Before implementation, run advise against the task intent, inspect actual sources and decide applicability; the candidate SKILL.md supplies an explicit operating rule, while automated enforcement in existing execution entrypoints is a separate future step.

Limitations: current preview cannot automatically measure external tokens/cost, assign owners to legacy records, infer undeclared file conflicts, verify semantic recurrence, or replace independent review. The CLI is available but not yet a mandatory preflight in existing workflows. A future explicit completion workflow needs scope-level evidence and human approval; the current backlog is a derived read-only projection.

## Stage 2: automatic evidence relationships and engineering memory

The candidate now exposes eight additional portfolio commands:
- graph ROOT [--project OWNER]: derive typed task/plan/intake/problem/report/repair relationships from declared fields and problem-register links. Reports are associated, not presumed passing.
- sync ROOT [--project OWNER]: compute current suggestion state from linked task/plan lifecycle and explicit completion receipt; raw intake captures remain unchanged. Mentions and reference-only associations are not coverage.
- accept-scope ROOT --project INTAKE_OWNER --id IDEA-ID --evidence '{"TASK-ID":"reports/attest.md"}' --expected-sha SHA --approve: explicitly approve that the full captured request is covered. Every linked implementation task must be closed with PASS, tracked unchanged exact acceptance-only review attestation and exact candidate. Plans must be implemented. A later changed scope/evidence reopens the derived view, not the historical receipt. New receipts append and reference the prior receipt hash.
- harvest ROOT [--project OWNER] [--task TASK-ID] [--limit N]: candidate source snippets with exact source SHA and line range; already captured identical ranges omitted. Semantic extraction is done by the current AI, not a second model. Unowned legacy records need reconciliation.
- learn ROOT --project OWNER --cause CAUSE --task TASK-ID --lesson TEXT --prevention TEXT --source RELPATH --start N --end N --source-sha SHA --expected-sha SHA --approve [--tags TAGS]: canonical per-project cause, append distinct evidence observations, exact replay idempotent, conflicting interpretations refused. New record expected SHA is SHA-256 of empty content. Source must be the task or an explicitly task-bound report. No arbitrary external files. Legacy record-lesson remains for compatibility; prefer learn for new captures.
- promote ROOT --project OWNER --cause CAUSE --level L2|L3|L4 --evidence EVENT_ID --expected-sha SHA --approve [--check CHECK_ID]: one-level explicit upgrade using exact current evidence. L1 captured, L2 operator-verified, L3 scoped mandatory rule, L4 built-in deterministic check. No arbitrary code or shell commands. Supported checks: lifecycle_consistency, declared_dependency_consistency, explicit_task_scope.
- recommendations ROOT [--project OWNER]: distinct evidence task counts and suggested escalation; does not promote.
- preflight ROOT --project OWNER [--task TASK-ID] [--query TEXT]: bounded task-family, tag and lexical relevance, verified rule reminders and supported checks. Fuzzy hits never block. Changed evidence downgrades promotion applicability. CLI context check automatically attaches this advisory, and for failed/deployed/closed tasks includes up to three harvest candidates. Only matching approved L4 checks can add a blocker; legacy release guards remain unchanged.

Design boundaries: existing Markdown and Git remain authoritative; no second state database, model API, daemon, cost collection or UI. No automatic scope closure from a matching title or deployed task. No automatic creation of lessons from ambiguous headings, semantic root cause determination or rule promotion. The current AI reviews evidence candidates; explicit owner authority is required to persist and promote. Approval provenance cannot be cryptographically established from a local file alone; independent review and owner authorization remain external responsibilities. This isolated candidate does not install itself or patch company production execution entrypoints. The candidate context-check integration applies when the candidate CLI is used. Historical lesson processing is incremental for exact captured source ranges, but discovery still reads source files on demand (no persistent index yet). Older records with unknown ownership are not assigned speculatively.
